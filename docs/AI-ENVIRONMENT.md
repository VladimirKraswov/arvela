# AI-среда: от OpenCode Desktop до двух GPU

Срез на **27 сентября 2026 года**. Здесь описана фактическая установка на Mac и
Proxmox, а не все возможности каталогов моделей или движков. Конфигурации, health,
`/v1/models`, `/provider`, `/mcp`, `/agent` и `/skill` проверены без новых
inference-бенчмарков. Секреты, ключи API и SSH-ключи намеренно не приводятся.

## Карта и поток одного запроса

```text
OpenCode Desktop 0.2.11 на Mac (Tauri 2 / React / TypeScript / Rust)
  ├─ интерфейс, проекты, черновики, вложения, диктовка, передача задач
  └─ OpenCode-сессия → http://127.0.0.1:4096 (OpenCode 1.18.18)
       ├─ по умолчанию: local-qwen-next/qwen38-flash-next
       │    → SSH-туннель 127.0.0.1:18019/v1
       │    → VM 5200, 192.168.31.71:1919
       │    → FreeToken → Flash Next NVFP4 → RTX 5090 + CPU/DDR4
       ├─ явно выбранная: local-qwen38/qwen-v100
       │    → SSH-туннель 127.0.0.1:18021/v1
       │    → VM 5100, 192.168.31.93:8080
       │    → NInfer → Qwen3.8-27B Huihui-abliterated NVFP4 → Tesla V100
       └─ отдельно: DeepSeek API — внешний сервис, не одна из локальных VM
```

**Работают две inference-VM, а не три.** FreeToken и Flash Next — движок и модель
на одной VM 5200. NInfer и 27B — движок и модель на VM 5100. VM 5090
`ai-media-inference` в Proxmox сейчас остановлена; это не третий участник
описанного запроса. Попытка вычислять один Flash Next-запрос сразу на 5090 и V100
оставлена: эти сервисы независимы, слои/эксперты между VM сейчас не передаются.

Desktop выбирает **движок агента**, модель, effort и сессию. В обычном режиме
движок агента — OpenCode: он хранит историю, вызывает инструменты и решает,
когда обращаться к модели. Место выполнения `bash`/чтения файлов — Mac с этим
OpenCode-сервером, даже если токены генерирует удалённая GPU. Для выполнения
инструментов на другой машине нужен отдельный удалённый OpenCode через SSH
или явное SSH-действие агента. OpenCode отправляет выбранные `providerID` и
`modelID` через совместимый с OpenAI HTTP API; ответ, рассуждения, вызовы
инструментов и статус приходят обратно в Desktop по API/потоку событий.
Desktop сам не запускает GPU-инференс и не подменяет модель другой при ошибке.

## VM 5200: RTX 5090, FreeToken и Qwen3.8 Flash Next

| Параметр | Фактическое значение |
| --- | --- |
| Proxmox | VM 5200 `ai-llm-5090`, `192.168.31.71`, SSH `vm-5200`; Q35/OVMF, passthrough RTX 5090 |
| Гость | Ubuntu 24.04.5 LTS, Linux 6.8.0-139, 32 vCPU с типом `host`, 160 GiB назначенной RAM, 400 GiB виртуальный SSD, ballooning выключен |
| CPU/GPU | Intel Xeon E5-2698 v4; GeForce RTX 5090, 32 607 MiB VRAM, compute capability 12.0; NVIDIA 595.91.07, CUDA toolkit 13.3.73 |
| Движок | Форк [FreeToken-5090-Lab](https://github.com/VladimirKraswov/FreeToken-5090-Lab), `main` `9ef483c`; живой checkout `/opt/freetoken/src/main-9ef483c`, Python-окружение `/opt/freetoken/venv` |
| Сервис/API | `freetoken-qwen.service`, `/srv/freetoken/serve.sh` → `deploy/rtx5090/serve.sh`; `:1919`, served ID `qwen38-flash-next`; на Mac туннель `:18019/v1` |
| Чекпойнт | [RadixArk/Qwen3.8-Flash-Next-NVFP4](https://huggingface.co/RadixArk/Qwen3.8-Flash-Next-NVFP4), revision `7b719225242aacd3dbd3f9407468c2ee9a9d2594`, `/srv/models/Qwen3.8-Flash-Next-NVFP4` (~130 GiB на диске) |
| Контекст | 262 144 токена: одновременно `FT_CONTEXT_TOKENS`, `FT_KV_RESERVE_TOKENS`, серверный `/v1/models`; один запрос в работе |

Это большая **MoE-модель** (около 125 млрд параметров всего,
`Qwen4ExpForConditionalGeneration`): 48 слоёв,
512 маршрутизируемых экспертов, top-10, GDN и QSA sparse attention, один PLE-слой,
Vision. Это другой чекпойнт и другая архитектура, чем 27B на V100. Выделенный KV-пул —
262 144 токена с BF16 KV. Настройки запуска: `--moe-strategy hybrid`,
автокэш экспертов, 12 CPU-потоков для экспертов, NVFP4 через Triton,
`--spec-mtp 3`, pinned PLE, radix/hybrid cache, prefill mixer 2,
бюджет prefill-чанка 0,85 и верхняя граница 14 336 токенов, доля VRAM-планировщика
0,87. Vision-энкодер и кэш его embeddings вынесены в RAM/CPU, максимум 4096
image-токенов. Сервер допускает до 32 768 выходных токенов, но OpenCode
объявляет этой модели максимум **16 384**. Модель принимает текст и изображения;
обычный OpenCode-выбор — Medium, хотя нативный сервер при неуказанном effort
может выбрать xhigh. Серверные sampling defaults: temperature 1, top-k 20,
top-p 0,95.

Слова «5090 + CPU/RAM» здесь имеют буквальный смысл. В VRAM лежат GPU-пулы
и горячие эксперты; значительная часть экспертных банков и PLE хранится в
оперативной памяти, а часть экспертной работы выполняют CPU-потоки. Движок
выбирает между доставкой нужных экспертов по PCIe и CPU-вычислением. Это
**не** деление слоёв между RTX 5090 и V100. На проверенном профиле VRAM почти
заполнена (около 31,8 GiB занято, сотни MiB свободны), поэтому увеличение
конкурентности, изображения или KV-пула без повторной проверки рискованно.

В форке реализованы и проверены: ограниченное чтение хвоста PLE при откате MTP
вместо копирования всей длинной истории; сокращение жизни временных тензоров
prefill; фиксированный MTP3; fused PLE row hashing из upstream PR с исправлением
времени жизни буферов CUDA Graph; устранение синхронизации CPU/GPU в инвалидаторе
prefill-слотов; выбор чанка по реально свободной VRAM; калибровка hybrid
CPU/GPU экспертного пути; проверки tool-calls, reasoning и Vision. Экспериментальный
адаптивный MTP измерен, но **выключен**: в контроле он был медленнее. В `main`
остался **опциональный** путь проверки NVFP4/Triton на Volta, но полный Flash Next
на V100 не квалифицирован и в production не включён. Последние изменения `main`
также касаются конфигурации агентского стека, изоляции daemon-тестов и сравнения
служебного токена за постоянное время. У сервиса включены watchdog и штатный
прогрев короткого ответа, sampling, длинного ввода и Vision.

Контекст меняется флагами запуска с последующим перезапуском **только** этого
сервиса, а не пересборкой FreeToken/Desktop. Затем надо согласовать лимиты
OpenCode в JSONC и обновить его конфигурацию в спокойный момент: OpenCode 1.18.18
не копирует новое значение из `/v1/models` автоматически. Сейчас OpenCode
объявляет `context=262144`, `input=245760`, `output=16384`. С резервом
автосжатия 24 576 порог составляет около **221 184** входных токенов.

## VM 5100: Tesla V100, NInfer и Qwen3.8-27B

| Параметр | Фактическое значение |
| --- | --- |
| Proxmox | VM 5100 `ai-gpu-v100`, `192.168.31.93`, SSH `vm-v100`; Q35/OVMF, passthrough V100 |
| Гость | Ubuntu 24.04.4 LTS, Linux 6.8.0-139, 16 vCPU Xeon E5-2698 v4, 64 GiB назначенной RAM, отдельный 128 GiB том модели |
| GPU | Tesla V100-SXM2-32GB, 32 768 MiB, SM70/Volta, лимит 300 W; NVIDIA 580.178.04, CUDA toolkit 12.9.86 |
| Движок | [Форк NInfer](https://github.com/VladimirKraswov/ninfer-v100), живой исходник `/srv/ninfer-v100-lab/engine/ninfer`, commit `ce67fc9` |
| Сервис/API | `ninfer-v100.service`, `192.168.31.93:8080`, served ID `qwen-v100`; на Mac туннель `127.0.0.1:18021/v1` |
| **Текущий** чекпойнт | `qwen3_8_27b_huihui_abliterated_nvfp4.ninfer`, ~21 GiB, в `/srv/ninfer-v100-lab/models/huihui-abliterated/` |
| Контекст | 262 144 токена и столько же KV-ёмкости; KV int8, MTP4, Vision, один исполняемый запрос |

Модель на V100 сейчас — **Huihui-abliterated NVFP4**, производная от
`huihui-ai/Huihui-Qwen3.8-27B-abliterated`, упакованная в NInfer v2. Это уже
не первоначальный стандартный 27B NVFP4 и не старый GGUF llama.cpp. Эффективный
systemd drop-in `10-huihui-uncensored.conf` заменяет путь чекпойнта из базового
unit; проверять только базовый unit недостаточно. Оригинальный NInfer-артефакт
сохранён отдельно для отката. Формат NVFP4 на V100 обслуживается программными
CUDA-ядрами; у Volta нет аппаратных FP4 Tensor Cores Blackwell. Это не означает,
что вся модель считается на CPU: наблюдаемый процесс занимает примерно
32,1 GiB VRAM, а веса текущего артефакта ~21 GiB. Для V100 не следует
приписывать FreeToken-гибридный CPU-offload: это другой сервер и профиль.

В production задано: `--max-context 262144`, `--kv-capacity 262144`,
`--kv-dtype int8`, `--spec mtp`, 4 черновых токена, LM-head draft,
`--prefill-chunk 2048`, `--vision`, сохранение thinking, максимум ответа
32 768, Medium по умолчанию с thinking budget 8192. Low использует 2048,
XHigh — 24576. Очередь ограничена 8 ожидающими запросами и 30 минутами;
параллельно исполняется один. OpenCode объявляет `context=262144`,
`input=229376`, `output=32768`, но в его 1.18.18 фактический запрашиваемый
потолок ответа в проверенном агентском ходе был 32 000. Автосжатие с тем же
резервом 24 576 начинается примерно на **204 800** входных токенах.

Из доработок форка: исправление воспроизведённой численной ошибки GDN на SM70
(контрольная проекция сохраняет FP32 до требуемой границы BF16), валидация и
передача `thinking_budget`, настройка default reasoning effort, ускорение
Vision-энкодинга и работы MTP с контекстом, ограниченная очередь для длинных
запросов, а также узкая починка однозначного текстового tool-call с пропущенным
тегом параметра (`ce67fc9`). Исправление не доказывает, что модель никогда не
ошибается при вызове инструментов. Старые GGUF, визуальный projector и
standalone llama.cpp unit из активной конфигурации удалены; отдельные архивы
и результаты сравнений сохранены. Для возврата к llama.cpp потребуется
восстановление runtime и весов; мгновенного переключателя нет.

Форк также содержит перенесённые на Volta оптимизации и альтернативную ветку
спекулятивного декодирования DFlash2. В текущем `ninfer-v100.service` явно
выбран **MTP4**, поэтому скорости DFlash2 из иных опытов нельзя считать
production-скоростью этого сервиса.

## Сохранённые измерения, без нового прогона

**Decode** — скорость появления выходных токенов после первого токена.
**TTFT** — ожидание первого видимого токена, включая обработку входного
контекста, очередь и служебные расходы. Чистый prefill указан только там,
где его отдельно считал движок. Числа ниже получены на разных моделях и
текстах: сравнивать между 5090 и V100 как цену одной и той же операции нельзя.

| Сценарий | Контекст/вход | Decode | Prefill или TTFT | Что можно заключить |
| --- | ---: | ---: | ---: | --- |
| FreeToken, 5090, текущий выбранный **262K** профиль, холодный синтетический код | 105 078 входных | **43,51 tok/s** | TTFT 42,76 с | 512 выходных, Medium, temperature 0; один прогон |
| Та же модель/профиль | 160 083 входных | **43,96 tok/s** | TTFT 62,99 с | Холодный ввод; один прогон |
| Та же модель/профиль | 240 083 входных | **43,35 tok/s** | TTFT 94,84 с | Близко к лимиту input OpenCode; один прогон |
| FreeToken, альтернативное окно **196K**, сопоставимые прогоны | 105 078 / 160 083 | 47,69 / 46,16 tok/s | TTFT 40,93 / 61,61 с | Отложенный вариант быстрее на 2–4 tok/s, но окно меньше; владелец выбрал 262K |
| FreeToken, прежний **131K**, реальный код ~104 870 входных | 131K окно | 42,59 tok/s (temperature 0); 37,86 при sampling | TTFT 40,48 / 40,06 с | Исторический другой прогон, **не** парный A/B с нынешним 262K |
| NInfer, первоначальный стандартный 27B NVFP4, выбранный MTP4 | 1267 / 29 961 входных | **81,54 / 66,04 tok/s** | Для холодных ~30K TTFT ~29,7 с | Эти цифры **не измеряли нынешние Huihui-веса** |
| NInfer, первоначальный 27B, холодный текст + изображение | 226 022 входных | **39,5 tok/s** | **391,5 tok/s prefill** движка; TTFT 577,94 с | Извлечены 3 факта и OCR; вся задача 604,43 с |
| Исторический llama.cpp на V100, иной GGUF/квантизация | ~2K / ~32K / ~160K | 58,5 / 44,4 / 22,1 tok/s | Для старого 225 810-токенного текста TTFT 944 с | Иллюстрирует прежнюю базу, **не** чистый A/B движков на одинаковых весах |

Для текущего **Huihui-abliterated** чекпойнта есть успешные короткие text/code/
Vision/Medium-smoke запросы, но нет нового полного сопоставимого бенчмарка
скорости или качества. Число **107/108** в отчёте NInfer относится к предыдущему
стандартному чекпойнту: код 51/51, математика 20/20, инструкции 15/16,
инструменты 11/11, Vision 10/10. Единственная ошибка была в точном развороте
строки; это smoke-suite, не гарантия общей «разумности». Старые 116/116 против
113/116 некорректно трактовать как нынешний вердикт: исходный эталон часов,
seed и повторы имели методические ошибки.

Результат 22,74 tok/s у прежнего двух-VM Flash Next pipeline против 40,74
tok/s у 5090+CPU в сопоставимом тесте — **исторический неудачный опыт**, а не
нынешняя скорость V100. Меж-VM pipeline удалён; V100 снова обслуживает 27B.
Также TTFT 94,84 с на 240K показывает рост времени чтения длинного ввода,
а не падение decode вдвое на текущем standalone-профиле.

## OpenCode на Mac: маршрутизация, агенты, инструменты

Установленный **OpenCode 1.18.18** обслуживает локальный API
`http://127.0.0.1:4096`; `/global/health` отвечает `healthy`. История,
статусы выполнения, разрешения и tool-calls принадлежат ему. Рабочая
конфигурация — `~/.config/opencode/opencode.jsonc`; JSONC и файловые
агенты/плагины живут отдельно от приложения Desktop. Глобальные default:
`model=small_model=local-qwen-next/qwen38-flash-next`, `default_agent=qwen-build`.
DeepSeek подключён как внешний провайдер с `deepseek-v4-pro` и
`deepseek-flash` (V4.1 Flash). OpenAI здесь не подключён. `opencode` (Zen)
отключён через `disabled_providers`, поскольку прежняя проверка бесплатного
доступа завершилась `FreeTierError`. `/provider` содержит большой справочный
каталог чужих сервисов; он **не означает**, что на каждый из них есть ключ.
Сейчас `/provider.connected` перечисляет только `deepseek`, `local-qwen-next`
и `local-qwen38`.

OpenCode передаёт модель в конкретном запросе. У модели на 5090 варианты
`low`, `medium`, `xhigh`; у V100 они же плюс явные thinking budget. Модель из
текущего ответа следует проверять в метаданных сообщения (`providerID`,
`modelID`), а не только по оставшемуся в композере названию. Внешний
DeepSeek-маршрут не использует локальные GPU; его доступность зависит от API
и сетевого пути, в том числе серверного VPN. Ключи в этой карте отсутствуют.

Настроено штатное автосжатие OpenCode: `auto=true`, `prune=true`, сохранение
6 последних ходов, 16 000 недавних токенов и резерв 24 576. Включены LSP,
formatter и snapshots; `tool_output` ограничен 400 строками/32 768 байтами.
Для основных `read`, `edit`, `bash`, поиска, web, task, skill, LSP и Todo
глобальная политика `allow`; для doom loop — `ask`. Это **разрешения инструмента
OpenCode, не системная песочница**. Агент/проект/сессия могут вводить свои
правила. Общая инструкция — `instructions/qwen-coding.md`.

Файловые агенты и встроенные роли, подтверждённые `/agent`:

| Агент | Роль |
| --- | --- |
| `qwen-build` | Основной coding-agent по умолчанию, Flash Next/Medium, план, проверки и checkpoint для существенных задач |
| `qwen-v100-build` | Основной coding-agent с выбранным 27B/V100/Medium и проверкой точных вычислений/строк |
| `qwen-review` | Read-only subagent на Flash Next, ограниченные команды Git, без записи |
| `build`, `plan`, `explore`, `general`, `compaction`, `summary`, `title` | Встроенные роли OpenCode; их наличие не означает отдельную модель или VM |

Два загруженных локальных plugin-файла видны в фактическом `/config.plugin`:
`qwen-flash-guardrails.js` соединяет Flash Next-инструкцию с системным prompt,
а `progress-guard.js` проверяет структуру Todo, напоминает о checkpoint через
8 существенных tool-вызовов и сохраняет критерии при compaction. Последний
**не блокирует** проверки. Отдельный собственный инструмент `repo_inspect`
даёт read-only обзор Git/манифестов/тестов. `/experimental/tool/ids` сейчас
перечисляет `question`, `bash`, `read`, `glob`, `grep`, `edit`, `write`, `task`,
`webfetch`, `todowrite`, `websearch`, `skill`, `apply_patch`, `lsp`,
`repo_inspect` и служебный `invalid`. Реальная доступность каждого вызова
дополнительно зависит от правил сессии.

`/skill` подтверждает встроенный `customize-opencode` и четыре локальных
навыка: `qwen-verify-change`, `qwen-browser-check`, `qwen-debug-regression`,
`opencode-desktop-computer`. Последний установлен Desktop для работы с Mac.
Из MCP подключены **два**, оба в статусе `connected`: `cua_desktop`
(`--computer-mcp`) и `opencode_desktop` (`--agent-mcp`). Оба запускают
установленный бинарник Desktop в режиме stdio; первый даёт ограниченное
управление окнами через Cua Driver, второй — семантическое управление
проектами, сессиями и задачами Desktop. CPU-помощник CT205 сейчас **не**
выдаёт MCP endpoint.

## Что добавляет OpenCode Desktop 0.2.11

Установлен `/Applications/OpenCode Desktop.app`, версия **0.2.11**.
Это не форк OpenCode и не inference-сервер: версия приложения, версия OpenCode
и версии FreeToken/NInfer независимы. OpenCode Desktop владеет интерфейсом,
локальными предпочтениями, списком проектов/подключений, черновиками,
очередью и индексом навигации; историю OpenCode, инструменты и модельные
запросы оставляет OpenCode. Дополнительный агент Pi имеет отдельное хранилище.

- Проекты раскрываются как папки с сессиями; есть «Недавние», поиск, архив,
  удаление сессий и обратимое **убирание проекта из списка** без удаления файлов.
  Чат возможен без Git-проекта и без выбранной папки: для него создаётся
  отдельный рабочий каталог. Локальный и удалённый SSH-серверы изолированы.
- В чате есть выбор модели, effort, агента и режима доступа; OpenCode — движок
  агента по умолчанию. Pi 0.85.1 — дополнительный **локальный** движок через
  JSONL RPC с собственными сессиями, настройками и LSP. Уже существующую
  сессию нельзя молча переинтерпретировать как Pi: перенос создаёт новый чат
  и показывает пользователю происхождение скопированного текста.
- Один пользовательский ход выглядит цельно: свёрнутые thinking/tool-шаги,
  отдельный итог, копирование ответа/кода, подсветка синтаксиса, даты и время.
  При прокрутке истории вверх автопрокрутка прекращается; «Вниз» её возвращает.
  Собственное сообщение можно исправить в новой ветке без переписывания истории.
  Индикаторы running/unread разделены по сессиям и проектам.
- Composer принимает Finder drag-and-drop, буфер, изображения и файлы до
  12 штук/50 MiB суммарно; большой вставленный текст становится `.txt`.
  Обе локальные модели нативно принимают текст и изображения. PDF превращается
  в текст и страницы, видео — в кадры и звуковую дорожку, аудио — в текст;
  лимиты и частичная выборка страниц видны пользователю. Диктовка отправляет
  запись в GigaAM и вставляет расшифровку в черновик, не посылая prompt.
- Настройки имеют поиск и категории: внешний вид/цвета/размеры шрифтов,
  соединения, модельные и OpenCode-инструменты, skills, plugins, MCP, agents,
  сервисы, Pi, диктовка, компьютер. Редактор JSONC сохраняет комментарии,
  показывает diff, создаёт backup и останавливается при конфликте записи;
  Desktop не перезапускает OpenCode автоматически.
- В заголовке можно **передать задачу** в выбранную сессию: сначала собрать
  цель, решения, файлы, проверки и следующий шаг из истории, затем прочитать
  и поправить пакет и только после этого отправить или сохранить черновик.
  Автоматический поиск другой сессии агентом не заявлен.
- Работа с Mac через Cua Driver использует отдельный курсор и разрешения
  macOS; возможности ограничены текущим Space и доступностью конкретного окна.
  Встроенный Agent Control MCP предлагает `desktop_status`, выбор проекта/
  сессии/модели, `desktop_send`, `desktop_wait`, `desktop_stop`, чтение истории
  и pending interactions без физической мыши. Он работает через приватный
  Unix-сокет и тот же видимый store, не подтверждает разрешения за пользователя.
- Опциональный Agent Factory для **явно управляемых** длительных задач требует
  точный маркер завершения, позволяет 0–20 ограниченных продолжений, checkpoint
  и восстановление метаданных после перезапуска Desktop. Он не включается
  автоматически для обычного UI-чата и не создаёт второй агентский цикл.

Mac-сборка и Linux `.deb` имеют отдельные platform overlays; Windows пока
архитектурный задел, не готовая сборка. Версия 0.2.11 прошла 297 frontend-
тестов (6 opt-in live пропущены), 32 Rust-теста, нативную проверку и сборку DMG;
это сведения из [verification](VERIFICATION.md), не новое тестирование здесь.

## Сервисы вокруг основного пути

| Сервис | Зачем и как подключён |
| --- | --- |
| CT201 `cpu-inference`, `192.168.31.59`, 40 vCPU/160 GiB | GigaAM v3 CPU ASR `gigaam-v3-e2e-rnnt` для диктовки/звука; Desktop направляет запись на `/api/asr/v1/audio/transcriptions` |
| CT205 `oc-helper`, Debian 12, 4 vCPU/4 GiB | `ffmpeg`, Poppler и Tesseract для PDF/аудио/видео; Mac-туннель `127.0.0.1:18107`, `/health` сейчас перечисляет `pdf`, `audio`, `video` |
| CT250 `xray-whitelist-gw`, 1 vCPU/2 GiB | Серверный VPN-шлюз для маршрутов некоторых внешних провайдеров; локальные Qwen через SSH-туннели от него не зависят |

CT205 не вычисляет LLM-токены и не заменяет Vision-модель: он готовит
неподдерживаемый напрямую формат. После обработки изображение/текст поступает
через OpenCode к **выбранной** модели. GigaAM тоже отдельный ASR, а не часть
FreeToken/NInfer.

## Быстрая проверка и границы этой карты

Без отправки нового inference-запроса можно сверить:

```sh
curl -fsS http://127.0.0.1:4096/global/health
curl -fsS http://127.0.0.1:18019/v1/models
curl -fsS http://127.0.0.1:18021/v1/models
curl -fsS http://127.0.0.1:18107/health
ssh vm-5200 'systemctl is-active freetoken-qwen.service'
ssh vm-v100 'systemctl is-active ninfer-v100.service'
```

`/v1/models` удостоверяет served ID/объявленное окно, но не доказывает
качество ответа. Для точного происхождения весов V100 нужно читать **эффективный**
`systemctl cat`, а не имя модели в меню: ID `qwen-v100` сохранён после замены
чекпойнта. Скорости выше — сохранённые измерения с указанными условиями;
нынешние веса V100 отдельно не перебенчмаркованы. Режим Pi, удалённый
OpenCode, внешние API и компьютерный MCP имеют собственные ограничения и не
обязаны проходить через обе локальные VM.
