# Управление OpenCode Desktop через MCP

OpenCode Desktop предоставляет локальный control plane для Codex, OpenCode и
других MCP-клиентов. Агенту не требуется двигать физическую мышь, распознавать
интерфейс по снимку или редактировать `localStorage` приложения.

## Подключение

1. Запустите установленный OpenCode Desktop. При старте он создаёт Unix-сокет и
   descriptor `~/.local/share/opencode-desktop/agent-control/control.json` (на
   Linux учитывается `XDG_DATA_HOME`). Каталог имеет режим `0700`, сокет и файл —
   `0600`; descriptor содержит случайный токен текущего процесса.
2. В приложении откройте **Настройки → API для агентов → Подключить MCP**. Desktop
   без потери комментариев добавит в глобальный JSONC OpenCode запись
   `opencode_desktop`, затем подключит её к текущему проекту через официальный
   `/mcp` API. Занятая чужой командой запись не перезаписывается.
   Первичную регистрацию также можно выполнить инструментом
   `desktop_install_mcp` уже запущенного standalone MCP-процесса.
3. В любом другом MCP-клиенте используйте установленный бинарник:

   ```json
   {
     "mcpServers": {
       "opencode_desktop": {
         "command": "/Applications/OpenCode Desktop.app/Contents/MacOS/opencode-desktop",
         "args": ["--agent-mcp"]
       }
     }
   }
   ```

   На Linux укажите путь к установленному `opencode-desktop`. Режим MCP не
   создаёт второе окно и не запускает второй OpenCode server.

## Рабочий цикл агента

1. `desktop_status` — проверить подключение, выбранные проект/чат/модель и
   незавершённые запросы пользователя.
2. `desktop_projects`, затем `desktop_sessions` — получить реальные идентификаторы.
3. `desktop_new_chat` либо `desktop_select` — выбрать точное место работы.
4. При необходимости `desktop_configure` — выбрать доступную модель, variant и
   агента. Политика разрешений этим API не повышается.
5. `desktop_send` вызывается один раз. Его ответ означает только принятие задачи.
6. `desktop_wait` ждёт `idle`, `needs_input`, `failed` или bounded timeout.
7. При `needs_input` прочитать `desktop_interactions`. Разрешения `once/always`
   допустимы только после явного решения пользователя; без такого решения можно
   только ждать или отклонить запрос. Ответы на вопросы нельзя выдумывать.
8. `desktop_conversation` возвращает ограниченную нормализованную историю и
   является источником финального результата.

`desktop_stop` останавливает конкретную сессию. Ожидание не блокирует status,
просмотр взаимодействий или stop из другого клиента. `desktop_set_view` открывает
панели приложения без pointer automation. Все команды сериализуются и проходят
через тот же frontend store, поэтому состояние MCP совпадает с видимым UI.

## Граница безопасности

- Listener — только Unix-сокет текущего пользователя; TCP/LAN-порт не открывается.
- На один запрос принимается не более 1 MiB, ответ ограничен 8 MiB, команда —
  шестью минутами, ожидание модели — пятью минутами за один вызов. Одновременно
  принимается до 32 соединений; незавершённый вход закрывается через 10 секунд.
- MCP не выдаёт shell и не меняет файлы напрямую. Файловые операции выполняет
  выбранный агент в рамках собственных разрешений OpenCode/Pi.
- Смена движка существующего чата запрещена: для другого движка создаётся новый
  чат, чтобы не подменять владельца transcript.
- При закрытии Desktop descriptor и сокет удаляются. После аварийного завершения
  старый descriptor безопасно заменяется новым при следующем старте.

## Диагностика

- `OpenCode Desktop control endpoint was not found` — приложение не запущено.
- `still starting` — WebView ещё не установил обработчик; повторите через секунду.
- `cannot connect` — descriptor остался от аварийно завершённого процесса;
  перезапустите Desktop.
- MCP подключён, но задача требует разрешения — это штатный `needs_input`, а не
  зависание. Откройте запрос в Desktop или передайте явный ответ через MCP.
