# Движок Pi

Второй **реально работающий** движок рядом с OpenCode. OpenCode остаётся
движком по умолчанию везде: проект или чат без явного выбора — это OpenCode.

Контракт взят из установленного дистрибутива:
`@earendil-works/pi-coding-agent@0.85.1`, файл `docs/rpc.md`. Ничего не
угадывалось — протокол проверен живыми запусками (см. «Приёмка»).

## Что Pi даёт и чего не даёт

| Возможность | Pi | Как это видно в UI |
|---|---|---|
| Потоковый текст, рассуждения, шаги инструментов | да | как у OpenCode |
| Остановка (`abort`) | да | кнопка «Стоп» |
| Долговечная история, пагинация | да, по `get_entries` | «Загрузить более ранние» |
| Сжатие контекста (`compact`) | да | пункт сжатия |
| Вложения | **только изображения** | остальное отклоняется с объяснением |
| PTY-терминал | нет | панель терминала скрыта |
| Панель изменений Git | нет | панель скрыта |
| Очередь разрешений OpenCode | нет | заменена диалогами расширений Pi |
| Ветвление сообщения (fork) | нет | кнопка правки скрыта |
| Удалённый хост | нет | Pi недоступен при выборе SSH-сервера |

Возможности объявляются в `PI_CAPABILITIES`, и UI скрывает неподдержанное, а не
показывает неработающие кнопки.

## Архитектура

```text
UI / src/state/store.ts
   │  engineForSession(): per-chat override → folder preference → OpenCode
   ├── AgentBackend "opencode"   → HTTP/SSE к отдельному серверу OpenCode
   └── AgentBackend "pi"         → src/agent/pi/
                                     backend.ts   сессии, промпты, подписки
                                     translate.ts Pi-события → модель приложения
                                     protocol.ts  типы RPC
                                     native.ts    мост к Tauri
                                        ↓ invoke / event
                                  src-tauri/src/pi.rs
                                        ↓ stdin/stdout JSONL
                                  pi --mode rpc --session-dir … --session-id …
```

Ключевое решение: **события Pi переводятся в собственный словарь событий
приложения** (`message.part.delta`, `message.part.updated`, `session.status`…),
поэтому существующий редьюсер, рендерер и логика прокрутки работают без
изменений. Второго цикла агента нет.

### Какой чат на каком движке

Предпочтение папки управляет **только новыми** чатами. Существующий чат
определяется по долговечным признакам:

```
явное переопределение чата → есть метаданные сессии Pi → OpenCode
```

Это важно: у всех чатов, созданных до появления выбора движка, записи нет. Если
бы запасным вариантом было предпочтение папки, то смена умолчания проекта на Pi
молча переинтерпретировала бы всю историю OpenCode как чаты Pi и отправила бы их
идентификаторы движку, который их никогда не видел.

Сменить движок у готового чата нельзя — у движков разные форматы истории и
разные хранилища. Выбор другого движка в композере открывает диалог переноса
(в обе стороны), а не тупиковое уведомление.

### Идентичность и изоляция сессий

- Проверки возможностей (каталог моделей, команды, проверка доступа) запускают
  Pi с `--no-session`, поэтому не оставляют транскрипта и не могут появиться в
  списке чатов.
- Идентификатор сессии генерирует приложение (`chat-<uuid>`), Pi запускается с
  `--session-id`; по документации он «использует ровно этот идентификатор,
  создавая сессию при отсутствии». Проверено: повторный запуск с тем же
  идентификатором возвращает ту же переписку.
- `--session-dir` — отдельный каталог на **каждый каталог проекта**
  (`app_data_dir()/pi-sessions/<FNV-дайджест>`), поэтому история одного проекта
  не может появиться в списке другого.
- Метаданные, которых нет в протоколе (заголовок, архив, происхождение при
  переносе), принадлежат приложению и лежат в настройках; сам транскрипт
  принадлежит Pi.

### Потоковые и долговечные идентификаторы

Во время стрима Pi ещё не сохранил сообщение и не сообщает его `id`. Транслятор
выдаёт **временные** идентификаторы вида `pi-live-assistant-N`, чтобы рисовать
текст немедленно. По событию `agent_settled` он просит перечитать историю, и
`get_entries` заменяет их на долговечные `id` записей. Это тот же приём
авторитетной пересинхронизации, что и при переподключении OpenCode.

## Безопасность

- **Никакой сети.** Транспорт — stdin/stdout дочернего процесса. Порт не
  открывается; по LAN ничего не экспонируется.
- **Программа только по абсолютному пути.** `PATH` не используется: каталог с
  правом записи не должен решать, какой агент запустится. Кандидаты:
  каталог приложения, `~/.local/bin`, `~/.bun/bin`, `/opt/homebrew/bin`,
  `/usr/local/bin`, плюс явно указанный в настройках абсолютный путь.
- **Один процесс на сессию.** Повторный `open` переиспользует живой процесс:
  дубликат писал бы в один и тот же append-only файл и отвечал бы дважды.
- **Завершение всего дерева процессов.** Pi сам порождает языковые серверы,
  поэтому сигнал только прямому потомку их бы осиротил. Последовательность:
  закрыть stdin (EOF) → ждать до 3 с → SIGTERM всей группе → ждать 1.5 с →
  SIGKILL группе. Pi запускается в собственной группе процессов
  (`process_group(0)`).
  Измерено: при закрытии stdin Pi выходит с кодом 0 и языковой сервер исчезает;
  Rust-тест `a_tree_that_ignores_eof_and_sigterm_is_still_fully_stopped`
  проверяет откат на дереве, которое игнорирует и EOF, и SIGTERM. Отдельно
  замечено: `typescript-language-server` умирает и при жёстком убийстве Pi, так
  как закрывается его stdin; групповой откат нужен для серверов, которые так не
  делают.
- **Встроенные инструменты Pi под запросом.** `write`, `edit`, `bash` и всё, что
  не входит в список заведомо read-only, проходят через расширение-шлюз
  (`resources/pi/tool-gate.ts`), которое приложение загружает в **каждую**
  сессию Pi. Оно вызывает `ctx.ui.confirm()`; в режиме RPC это
  `extension_ui_request`, который приложение показывает модальным окном.
  Неизвестные инструменты требуют подтверждения (fail closed). Отказ по
  умолчанию: если показать диалог некому или ответа нет до дедлайна, нативная
  сторона отвечает `cancelled: true`. Молчание — это отказ.
  Полный доступ без запросов существует, но только как **явный** выбор
  пользователя в «Настройки → Движок Pi → Доступ Pi к инструментам»; значение по
  умолчанию и любое неизвестное значение трактуются как «спрашивать».
- **Ключи провайдеров приложение не трогает.** Pi берёт их из своего окружения
  или своего хранилища. Приложение их не читает, не показывает и не сохраняет;
  в настройках отражается только готовность.

## Выбор движка

- Папка проекта имеет предпочтение (`prefs.projectEngine`), по умолчанию
  OpenCode. Существующие проекты и чаты записи не имеют — это и есть миграция.
- Чат наследует предпочтение папки и **закрепляет** движок за собой при
  создании (`prefs.sessionEngine`), поэтому перезапуск маршрутизирует его верно.
- Готовый чат нельзя перевести на другой движок: у движков разные транскрипты и
  разные хранилища. Вместо этого есть явный перенос (ниже).
- Выбор модели хранится отдельно для каждого движка. OpenCode сохраняет прежние
  ключи без префикса, поэтому существующие настройки продолжают работать.
- Pi не зависит от состояния OpenCode: чат Pi работает и при недоступном
  сервере OpenCode.

## Модели

Встроенный каталог Pi — **не** список доступных аккаунту моделей. Он может и не
знать модель, которая работает (у этого аккаунта `deepseek-flash`: Pi
предупреждает, что идентификатор не из каталога, и корректно работает с ним как
с пользовательским), и перечислять модели, к которым доступа нет.

Поэтому:

- в настройках есть поле «Свой идентификатор модели» (`provider/model`), которое
  используется независимо от каталога;
- каталог Pi показан в настройках, где каждую модель можно проверить отдельно;
  там же проверяется пользовательский `provider/model`;
- в выборе модели чата видны **только проверенные** модели; проверка отправляет
  один минимальный реальный запрос в эфемерной сессии и требует содержательного
  ответа без ошибки. Результат хранится отдельно для каждого идентификатора;
  повторная неудачная проверка убирает его из списка. Настроенная модель сама по
  себе ничего не доказывает о ключах, эндпоинте или правах.

## Перенос контекста между движками

Полного бесшовного продолжения не существует и оно не заявляется. Перенос
работает **в обе стороны** (OpenCode → Pi и Pi → OpenCode):

1. История исходного чата **остаётся на месте** и не переписывается.
2. Создаётся **новый** чат целевого движка в той же папке; в его метаданных
   сохраняется `handoffFrom`.
3. В черновик кладётся расшифровка с явной шапкой: «Это НЕ твои прошлые
   сообщения: их писал другой агент в другой сессии». Шаги инструментов
   пересказываются, а не выдаются за выполнимые.
4. Ничего не отправляется, пока пользователь не нажмёт «Отправить»: расшифровка
   попадает в черновик и её можно прочитать и отредактировать.
5. В новом чате видна плашка происхождения со ссылкой на исходный чат.

Шаги инструментов переносятся с результатом (путь/команда и сокращённый вывод),
а не одним лишь именем: следующему агенту нужен итог, а не указание. Если всё не
помещается в лимит (48 000 символов), сначала сокращается вывод инструментов, и
только потом отбрасываются самые ранние реплики — и то и другое сообщается и в
шапке расшифровки, и в плашке происхождения.

## LSP

Требование владельца — поддержка языковых серверов для Pi, отдельно от OpenCode.

### Аудит стороннего кандидата

`https://github.com/samfoy/pi-lsp-extension` @ `f2433d19c3bb1300dfdc5f4505b062f9c9c0a1a6`
(v1.3.0) прочитан в клоне, **не устанавливался**. Что найдено:

- ~8 400 строк TypeScript; зависимости `web-tree-sitter` (WASM),
  `tree-sitter-wasms`, `vscode-languageserver-protocol`; во время работы
  требуется разрешить `jiti`.
- Сетевых вызовов нет; используется **Unix-сокет**, не TCP — по LAN ничего не
  экспонируется. Это хорошо.
- Но: он запускает **отсоединённый демон** на рабочее пространство, который
  переживает сессию Pi, со своим PID-файлом и сокетом. Приложение обещает, что
  ни один потомок агента не переживает окно, а этим демоном оно не владеет.
- Содержит специфичную для организации логику («Brazil workspaces»,
  `bemol-extension`), не относящуюся к этому репозиторию.
- Команды серверов по умолчанию ищутся в `PATH`.

Вывод: для нашей модели владения процессами он не подходит. Решение —
**собственное минимальное расширение**, а не установка стороннего.

### Что реализовано вместо него

`src-tauri/resources/pi/lsp-extension.ts` (~430 строк, читается целиком):

- языковой сервер — **прямой потомок процесса Pi** по stdio; ни демона, ни
  сокета, ни PID-файла; умирает вместе с сессией;
- список серверов читается только из файла, который пишет само приложение
  (`OCDESKTOP_LSP_CONFIG`); файлы проекта не выбирают, что запускать;
- каждый путь обязан быть абсолютным и существовать; `PATH` не используется;
- перед предложением сервера проверяется, что он реально запускается
  (`rustup` создаёт шим `/usr/bin/rust-analyzer` даже для неустановленного
  компонента — этот случай пойман живым тестом);
- все ожидания ограничены таймаутами; упавший сервер сообщается, а не
  перезапускается в цикле;
- инструменты: `lsp_diagnostics`, `lsp_hover`, `lsp_definition`.

Конфигурация пользователя `~/.pi` **не изменяется**: расширение передаётся
явным `--extension <абсолютный путь>` из каталога приложения.

На macOS установлены TypeScript Language Server и rust-analyzer; нативное
приложение показало оба как «готов». Кнопка «Настроить LSP» сообщает
фактически найденные серверы, а не предполагает их наличие.

## Приёмка на Linux (Ubuntu 24.04)

Ключ DeepSeek использовался только в окружении дочерних процессов, не печатался
и не попадал в аргументы, файлы репозитория или логи.

- `test/pi-live.test.ts` (opt-in, реальный `pi --mode rpc` + реальная модель):
  потоковый ответ дошёл до состояния чата приложения (`PI_LIVE_OK`),
  `agent_settled` переключил историю на долговечные `id`, один процесс на
  сессию, повторное открытие той же сессии вернуло тот же транскрипт.
- LSP вживую: модель вызвала `lsp_diagnostics` на фикстуре и получила
  `Type 'number' is not assignable to type 'string'` (typescript-language-server)
  и `E0308 mismatched types` (rust-analyzer).
- Шлюз инструментов вживую: модель получила прямое указание записать файл,
  действительно вызвала `write`, шлюз запросил подтверждение, ответ был
  «отклонено» — файл не создан. Тест проверяет и сам факт попытки, и факт
  запроса, чтобы не быть вакуумным.
- Собранное приложение: раздел «Движок Pi» показал путь и версию 0.85.1,
  каталог моделей, прочитанный у самого Pi, и кнопка «Настроить LSP» нашла оба
  сервера как «готов». Каталог Pi перечисляет больше моделей, чем авторизовано
  аккаунту (`/models` даёт `deepseek-flash` и `deepseek-v4-pro`), поэтому в
  выборе они помечены как непроверенные, а не как доступные.
- После выхода из приложения не осталось ни одного процесса Pi.

На macOS после этого этапа отдельно проверены обе локальные Qwen через Pi и
нативный проектный чат без проекта: `PI_FINAL_OK`, сохранение истории и
корректное окно контекста 131 072. Подробности в `docs/VERIFICATION.md`.

Не проверялись: Windows (варианта нет), диалоги сторонних расширений Pi
(шлюз приложения проверен вживую, остальные расширения — юнит-тестами) и
вложения-изображения в Pi в живом запросе.
