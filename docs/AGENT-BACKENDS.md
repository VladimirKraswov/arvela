# Слой агент-бэкенда

## Что реализовано

Реализовано **два** бэкенда:

- **`opencode`** — движок по умолчанию везде. Папка или чат без явного выбора
  работает на OpenCode.
- **`pi`** — локальный агент Pi через его режим RPC. Рабочий, с проверкой на
  живых запусках; см. [docs/PI-ENGINE.md](PI-ENGINE.md), включая то, чего Pi
  **не** умеет.

Второго цикла агента нет: события Pi переводятся в тот же словарь событий, что
и события OpenCode, и обрабатываются существующим редьюсером.

## Границы

```text
src/components/       презентация
src/state/store.ts    выбор проекта/сессии, редьюсер потока, действия
        ↓ вызывает только AgentBackend
src/agent/backend.ts  нейтральный контракт (типы, возможности, подписки)
src/agent/registry.ts реестр дескрипторов; по умолчанию opencode
src/agent/opencode.ts OpenCodeClient + два SSE-потока
src/agent/pi/         Pi: RPC-протокол, трансляция событий, нативный мост
        ↓ loopback HTTP/SSE/WebSocket
отдельно установленный сервер OpenCode
```

- `store.backend` — подключение и проекты OpenCode. Боковая панель объединяет
  сессии OpenCode и метаданные локальных чатов Pi; отсутствие сервера OpenCode
  не скрывает чаты Pi.
- `store.conversation()` — движок **открытого чата**; именно ему уходят промпт,
  история, остановка и сжатие. Выбор описан в `src/state/engines.ts`.
- Оба движка зарегистрированы в реестре, поэтому `listBackendDescriptors()` —
  честный список того, чем эта сборка умеет управлять.
- Транспорт принадлежит бэкенду. URL, формат SSE и заголовки наверх не уходят:
  `subscribeDirectory` и `subscribeAll` принимают колбэки, а не адреса.
- `AgentBackend.capabilities` описывает необязательные поверхности
  (`pty`, `fork`, `compaction`, `projectlessChat`, …). UI деградирует по
  возможности, а не по версии сервера.

## Намеренный «эвакуационный люк»

Часть поверхностей действительно специфична для OpenCode и в нейтральный контракт
не входит: PTY-WebSocket терминала, инвентарь `/mcp` и редактор JSONC-конфигурации.
Они получают клиента через `asOpenCodeClient(backend)`, который возвращает `null`
для любого другого бэкенда, — вызывающая сторона обязана сначала проверить
возможность, а не предполагать OpenCode. `store.client` — тот же люк для
существующих компонентов; при не-OpenCode бэкенде он бросает явную ошибку.

## Как добавить бэкенд

1. Реализовать `AgentBackend` (`src/agent/backend.ts`).
2. Описать `AgentBackendDescriptor`: `id`, `label`, `defaultEndpoint`,
   `capabilities`, `isAllowedEndpoint` (модель безопасности адреса),
   `normalizeEndpoint`, `create`.
3. Вызвать `registerBackendDescriptor(...)` (см. регистрацию Pi в конце
   `src/state/store.ts`).
4. Добавить идентификатор в `engineOptions()` (`src/state/engines.ts`), чтобы он
   появился в выборе движка вместе с причиной недоступности.

Правила, обязательные для любой реализации:

- каждый вызов, зависящий от каталога, несёт этот каталог явно;
- `prompt` подтверждает **приём** задачи, а не её завершение; прогресс приходит
  событиями;
- запросы разрешений и вопросы показываются пользователю и никогда не
  подтверждаются автоматически;
- переподключение сначала пересинхронизирует авторитетную историю/статусы и
  ожидающие запросы, затем продолжает инкрементальные обновления.

## Тесты

`test/agent-backend.test.ts` фиксирует: OpenCode остаётся зарегистрированным
умолчанием, неизвестный идентификатор откатывается к умолчанию, адрес проверяется
моделью безопасности OpenCode, адаптер передаёт аргументы без добавления
умолчаний, а посторонний дескриптор регистрируется, не меняя активный бэкенд.
